1  About the Application

MyHourly is an HRMS (Human Resource Management System) exposed as a Spring Boot REST API. The repository is backend-only; a separate frontend application (which consumes the API on port 3000) is out of scope for this guide but is touched on in §5.

  • Scheduled jobs (must always run — require one long-running instance, not serverless):

Minimum services, stated plainly
Every path needs exactly three categories of AWS services: 1) compute to run the container (ECS/Fargate, EC2, or Beanstalk), 2) a PostgreSQL database (RDS — or Postgres on the same VM in path C), and 3) Amazon S3 for files. Everything else in this guide is supporting or optional.

3  Minimum Required AWS Services

3.1 Amazon ECS on Fargate (compute) — or EC2

Runs the Dockerized Spring Boot API on port 8080. The existing Dockerfile builds and runs the app unchanged. Fargate removes server management; the alternative is EC2 (self-managed VM, cheaper at idle). Because the app embeds @Scheduled jobs, the compute must run one task 24×7 — keep desiredCount = 1 (§13.3).

  • Start size: 1 vCPU / 2 GB memory (Fargate) — comfortable for Spring Boot + Hikari pool (max 8 connections) + POI/PDF generation.
  • Storage: none needed locally — everything is in RDS + S3 (Fargate's ephemeral 20 GB layer is enough for temp files during report export).

3.2 Amazon RDS for PostgreSQL (database)

The app is JPA/PostgreSQL — spring.datasource.* (prod profile) already expects a JDBC URL, user and password from env vars. RDS replaces the current Aiven instance 1:1, and adds managed backups, Multi-AZ and PITR.

  • Start size: db.t4g.micro (2 vCPU / 1 GB RAM) or db.t4g.small (2 GB RAM) — single-AZ to save money; enable automated backups (7 days) and rds.force_ssl=1.
  • Note: the app runs spring.jpa.hibernate.ddl-auto=update — RDS is fine with it; see §13.5.

3.3 Amazon S3 (object storage)

Replaces Backblaze B2. The storage layer (B2FileStorageServiceImpl) already uses the AWS SDK for Java (S3Client + S3Presigner) and reads five config properties (b2.bucket, b2.access-key, b2.secret-key, b2.endpoint, b2.region). These map directly to an S3 bucket + IAM user keys — only the endpoint/region values change. No code change required.

  • Create one bucket, e.g. myhourly-files, with Block Public Access ON — the app returns short-lived presigned URLs, so the bucket itself never needs to be public.
  • Configure the app with the values in §6.2 Step 4.

5  Optional Services

ServicePurposeWhen to add
Application Load Balancer HTTPS termination, target health checks, domain routing As soon as you expose the API publicly — but see the 1 MB body limit warning below
Amazon Route 53 DNS for api.yourdomain.com When you have a domain ($0.50/hosted zone/month + query cost)
AWS Certificate Manager (ACM) Free TLS certificates for ALB Together with ALB + Route 53
Amazon CloudFront CDN in front of the frontend static site and/or presigned file URLs For the React frontend (S3 static hosting) — recommended
NAT Gateway Outbound internet for tasks in private subnets Only if you use a private-subnet architecture (~$32/month — skip to save money; public subnets + SG rules work fine here)
AWS WAF Web-application firewall on the ALB Later hardening; not required to go live
⚠ Application Load Balancer has a 1 MB request-body limit — affects file uploads
The app uploads files through the API (multipart, up to 25 MB per the storage service, 100 MB Spring limit). ALB rejects request bodies over 1 MB with 413 Request Entity Too Large, so profile photos / announcements / documents over 1 MB will fail behind an ALB. Options: (a) add a presigned-PUT upload endpoint so the browser uploads straight to S3 and the API only stores the key (small code change — recommended), (b) use a Network Load Balancer instead (no body limit; TLS via ACM), or (c) accept the limit and cap uploads at ≤ 1 MB. Path C (direct EC2 IP) and path B (Beanstalk single instance without ALB) do not have this problem.

6.2 Step-by-step

Step 1 — Prepare the code & secrets (do this first)

  1. Remove hardcoded credentials. application-dev.properties currently contains live-looking Aiven, Gmail and JWT values. For AWS, run with SPRING_PROFILES_ACTIVE=prod (already 100% env-var driven) and rotate/remove the old credentials before going live (§11).
  2. Add a real health endpoint (recommended). /actuator/health is whitelisted in SecurityConstants, but spring-boot-starter-actuator is not on the classpath. Either add it, or point the ALB health check at /swagger-ui/index.html (public, returns 200).
  3. Build the image locally once to smoke-test: ./mvnw clean package -DskipTests then docker build -t myhourly:local .

Step 2 — Store secrets in AWS Secrets Manager

Create these secrets (all read by ECS via the task definition in §6.3):

SecretKeys (JSON)Example value
myhourly/dbDATABASE_URL, DATABASE_USER, DATABASE_PASSWORDjdbc:postgresql://myhourly.xxxx.us-east-1.rds.amazonaws.com:5432/myhourly
myhourly/jwtJWT_SECRET, ACCESS_TOKEN_EXPIRATION, REFRESH_TOKEN_EXPIRATION512-bit random secret; 9000000 / 604800000 ms
myhourly/smtpSMTP_USERNAME, SMTP_PASSWORD, SMTP_HOST, SMTP_PORTSES SMTP user / password, or your Gmail app password
myhourly/storageB2_BUCKET_NAME, B2_ACCESS_KEY, B2_SECRET_KEY, B2_ENDPOINT, B2_REGION, B2_PUBLIC_URLSee Step 4

Step 3 — Create the RDS PostgreSQL database

aws rds create-db-instance \
  --db-instance-identifier myhourly-db \
  --engine postgres \
  --engine-version 16 \
  --db-instance-class db.t4g.micro \
  --allocated-storage 20 \
  --master-username myhourly \
  --master-user-password 'CHANGE_ME_STRONG' \
  --db-name myhourly \
  --backup-retention-period 7 \
  --publicly-accessible false \
  --vpc-security-group-ids sg-xxxxxxxx
# After creation, set parameter rds.force_ssl=1 (DB parameter group)

Take note of the endpoint (e.g. myhourly-db.xxxxxxxx.us-east-1.rds.amazonaws.com) — it goes into the myhourly/db secret as DATABASE_URL.

Step 4 — Create the S3 bucket + IAM user

aws s3api create-bucket --bucket myhourly-files --region us-east-1
aws s3api put-public-access-block --bucket myhourly-files \
  --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

# IAM user with programmatic access, policy scoped to this bucket only (§6.4)
aws iam create-user --user-name myhourly-s3
aws iam create-access-key --user-name myhourly-s3

Map the app's b2.* properties to S3 (stored in the myhourly/storage secret):

App propertyValue for AWS S3
b2.bucketmyhourly-files
b2.access-keyIAM access key id
b2.secret-keyIAM secret key
b2.endpointhttps://s3.us-east-1.amazonaws.com (or omit for the SDK default)
b2.regionus-east-1
b2.public-urlUnused for presigned URLs — can be left empty
Why the presigned-URL model makes S3 migration easy
The storage service writes objects with the S3 SDK and returns a 15-minute presigned GET URL. Point the same code at S3 and it works identically — no public bucket, no ACLs. (Note: if any code path stores the presigned URL itself rather than the object key, that URL will expire after 15 minutes — worth auditing during migration, §9.)

Step 5 — Build & push the image to ECR

aws ecr create-repository --repository-name myhourly

aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin ACCOUNT_ID.dkr.ecr.us-east-1.amazonaws.com

docker build -t myhourly:latest .
docker tag myhourly:latest ACCOUNT_ID.dkr.ecr.us-east-1.amazonaws.com/myhourly:latest
docker push ACCOUNT_ID.dkr.ecr.us-east-1.amazonaws.com/myhourly:latest

Step 6 — Register the ECS task definition & create the service

Register the task definition from §6.3 (via console or aws ecs register-task-definition), then:

aws ecs create-service \
  --cluster myhourly-cluster \
  --service-name myhourly-api \
  --task-definition myhourly-api:1 \
  --desired-count 1 \
  --launch-type FARGATE \
  --network-configuration "awsvpcConfiguration={subnets=[subnet-xxx,subnet-yyy],securityGroups=[sg-xxx],assignPublicIp=ENABLED}" \
  --load-balancers "targetGroupArn=arn:aws:elasticloadbalancing:...:targetgroup/myhourly-tg/...,containerName=myhourly-api,containerPort=8080"
  • Region/timezone: any region works — the container already forces TZ=Asia/Kolkata and -Duser.timezone=Asia/Kolkata.
  • Networking: public subnets + SG that only allows 8080 from the ALB SG (avoids a $32/month NAT gateway).

Step 7 — ALB, HTTPS and Route 53

  1. Create an internet-facing ALB; target group on port 8080, health check path /swagger-ui/index.html (or /actuator/health if you added actuator), healthy threshold 3, interval 30 s.
  2. Request an ACM certificate for api.yourdomain.com (DNS validation) and attach it to an HTTPS:443 listener with HTTP→HTTPS redirect.
  3. Create a Route 53 A record (alias) pointing api.yourdomain.com at the ALB.
  4. Set PASSWORD_RESET_FRONTEND_URL to your real frontend reset-password page (e.g. https://app.yourdomain.com/reset-password) in the task environment.

Step 8 — Migrate data & files (see §9)

Restore the Aiven dump into RDS and copy B2 objects into S3 before switching traffic.

Step 9 — Verify

  • GET https://api.yourdomain.com/swagger-ui/index.html → 200 (or /actuator/health → {"status":"UP"}).
  • Log in via POST /api/v1/auth/login; check the Swagger UI loads.
  • Upload a file (≤ 1 MB if behind ALB — §5 warning) and confirm a presigned URL is returned.
  • Confirm RDS is receiving connections: CloudWatch logs show no datasource errors; Hikari pool = 8 max.
  • Watch /ecs/myhourly log group for the seeders running once (they skip existing rows).

6.4 IAM roles & policies

Execution role — ecsTaskExecutionRole

Managed policy AmazonECSTaskExecutionRolePolicy (ECR pull + logs) plus read access to the Secrets Manager secrets:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "secretsmanager:GetSecretValue",
      "kms:Decrypt"
    ],
    "Resource": [
      "arn:aws:secretsmanager:us-east-1:ACCOUNT_ID:secret:myhourly/*",
      "arn:aws:kms:us-east-1:ACCOUNT_ID:key/*"
    ]
  }]
}

Task role — myhourly-task-role (what the app's SDK calls use)

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::myhourly-files",
        "arn:aws:s3:::myhourly-files/*"
      ]
    },
    {
      "Effect": "Allow",
      "Action": ["ses:SendEmail", "ses:SendRawEmail"],
      "Resource": "*"
    }
  ]
}
Prefer task roles over access keys
The task role above makes static keys unnecessary for S3/SES. However, the app reads b2.access-key / b2.secret-key directly, so it expects static keys. Two options: keep a dedicated IAM user myhourly-s3 with the S3 policy (simplest, zero code change), or modify B2StorageConfig to build S3Client from the instance role when keys are absent. The guide uses the IAM-user approach.

7  Alternative A — Elastic Beanstalk (Simplest)

If you prefer a managed platform without ECS/IAM details: deploy the single Docker container to Elastic Beanstalk and keep RDS + S3 as in §6.

  1. Create RDS and S3 exactly as in §6.2 Steps 3–4; store the same secrets in Secrets Manager (or plain env vars in EB for speed — use Secrets Manager for production).
  2. In the EB console: Create environment → Web server environment → Docker platform (single-container), upload a zip of the project (EB builds from the Dockerfile).
  3. Set environment properties: SPRING_PROFILES_ACTIVE=prod, DATABASE_URL, DATABASE_USER, DATABASE_PASSWORD, JWT_SECRET, token expirations, SMTP vars, B2_* vars, PASSWORD_RESET_FRONTEND_URL.
  4. Choose instance type t4g.small (2 GB RAM), root volume 20 GB. EB adds a reverse proxy on port 80 → 8080 automatically.
  5. Point api.yourdomain.com (Route 53 + ACM) at the EB environment URL; enable HTTPS via the EB load balancer or environment domain.
  6. Deploy updates with eb deploy.
  • No ALB by default — single instance uses its own proxy, so the 1 MB body limit does not apply.
  • EB single instance ≈ $15/month (t4g.small) + RDS ≈ $14 → ≈ $30–40/month total.

8  Alternative B — Single EC2 + docker-compose (Cheapest)

One VM runs both the app and PostgreSQL as containers. Fine for dev/staging or a very small team; you manage backups and upgrades yourself.

Steps

  1. Launch an EC2 t4g.small (2 vCPU / 2 GB, Amazon Linux 2023), 20 GB gp3 EBS, SG allowing 80 (and 22 from your IP only). Associate an Elastic IP.
  2. Install Docker + compose: sudo dnf install -y docker && sudo systemctl enable --now docker, then sudo usermod -aG docker ec2-user (re-login).
  3. Clone the repo on the instance; add the docker-compose.yml below; create a .env with all secrets.
  4. docker compose up -d --build
  5. Point api.yourdomain.com at the Elastic IP. HTTPS: install Caddy/nginx as a reverse proxy (TLS via Let's Encrypt), or add an ALB later.

docker-compose.yml

Cheapest ≠ production-safe
Single-VM Postgres has no managed backups/HA. If the VM dies, so does the database (unless you add nightly pg_dump to S3). Use this path for dev/experiments; move the DB to RDS for production.

9  Data & File Migration

9.1 Database: Aiven PostgreSQL → RDS

# 1) Dump from the current Aiven instance (custom format preserves types)
pg_dump "postgresql://avnadmin:****@pg-11fc3ab8-hourlyrecruittechlabs-d432.a.aivencloud.com:16410/defaultdb?sslmode=require" \
  --format=custom --no-owner -f myhourly.dump

# 2) Create the empty database on RDS (already created via --db-name in §6.2 Step 3; skip if present)
psql "postgresql://myhourly:****@myhourly-db.xxxxxxxx.us-east-1.rds.amazonaws.com:5432/postgres" \
  -c "CREATE DATABASE myhourly;"

# 3) Restore (run once; app seeders will skip existing rows afterwards)
pg_restore --no-owner --no-privileges \
  -d "postgresql://myhourly:****@myhourly-db.xxxxxxxx.us-east-1.rds.amazonaws.com:5432/myhourly" \
  myhourly.dump

# 4) Sanity check row counts
psql "postgresql://myhourly:****@myhourly-db.xxxxxxxx.us-east-1.rds.amazonaws.com:5432/myhourly" \
  -c "SELECT count(*) FROM users; SELECT count(*) FROM employees;"
  • Do this during a maintenance window; the app tolerates it because seeders skip existing records.
  • Keep the Aiven instance running until the switch-over is verified, then decommission it.

11  Security Checklist

  1. Rotate & remove hardcoded credentials. application-dev.properties ships live-looking Aiven, Gmail and JWT values. Rotate the Aiven/Gmail credentials and ensure no AWS deployment uses them.
  2. All secrets in Secrets Manager — JWT secret, DB password, SMTP password. Never in the repo, task definition plaintext, or image layers.
  3. RDS: private subnet; security group allows 5432 only from the ECS task SG (or a bastion); rds.force_ssl=1; automated backups ≥ 7 days; Multi-AZ for production SLA.
  4. S3: Block Public Access ON; versioning on; lifecycle to archive/expire old versions. The app's presigned URLs need no public access.
  5. IAM least privilege — task role scoped to the single bucket (§6.4); no s3:* wildcards across buckets; no long-lived keys where a role works.
  6. JWT: use a fresh random secret ≥ 64 bytes; store token expirations from env (access 2.5 h, refresh 7 d as in dev defaults — tighten for production if desired).
  7. HTTPS everywhere — ACM cert on ALB, HTTP→HTTPS redirect; PASSWORD_RESET_FRONTEND_URL must be HTTPS.
  8. Security groups — ALB: 443/80 from 0.0.0.0/0; ECS task: 8080 from ALB SG only; no SSH except bastion/VPN. WebConfig CORS is allowedOrigins("*") — restrict to your frontend origin for production.
  9. Audit — enable CloudTrail (management events) and consider GuardDuty; both are cheap at low volume.
  10. Schema control — ddl-auto=update is acceptable to start; move to Flyway/Liquibase migrations before schema churn becomes risky (§13.5).
  11. Frontend CORS — SecurityConfig/WebConfig currently allow all origins; lock to https://app.yourdomain.com.

13  Operations, Monitoring & Known Gotchas

13.1 Monitoring

  • Logs: awslogs → CloudWatch group /ecs/myhourly; set retention (e.g. 30 days) to cap cost.
  • Alarms: CPUUtilization > 80% (5 min), HTTPCode_Target_5XX_COUNT > 0, DB Connections > 80% of pool (8), failed ECS deployments.
  • RDS: monitor free storage, replica lag (if Multi-AZ/read replica), and slow-query logs.
  • SES: bounce/complaint rate via the SES console (keep < 5% / < 0.1%).

13.2 Backups & restore

  • RDS automated backups (7 days, PITR) — test a quarterly restore into a scratch instance.
  • S3 versioning enabled; add lifecycle to expire old versions after 90 days.
  • Document the restore runbook (console steps + the pg_restore command in §9.1).

13.3 Scaling (important: schedulers)

  • The in-app @Scheduled jobs mean you must keep exactly one long-running task. desiredCount = 1; do not attach a CPU-based autoscaler that spawns a second task (you'd get duplicate notifications/attendance runs).
  • If load outgrows one task: add a second task running only the API, and a separate scheduler-only task (same image, a profile/env flag that disables @EnableScheduling on the API tasks). That's a small code change — worth planning.
  • Scale up (2 vCPU / 4 GB) before scaling out.

13.4 Timezone & schedulers

  • The Dockerfile already sets TZ=Asia/Kolkata and -Duser.timezone=Asia/Kolkata — cron jobs fire on IST regardless of the AWS region.
  • Verified schedulers: Attendance (1 min), Notifications (5 min), Birthday/Holiday/WorkAnniversary (daily), Leave (Jan 1 & month-end).

13.6 Frontend note

The repo contains the backend API only. The frontend (React, expected at port 3000 locally) should be hosted separately — e.g. static files in S3 behind CloudFront + ACM, or AWS Amplify — and PASSWORD_RESET_FRONTEND_URL / CORS origins updated to the real domain.
