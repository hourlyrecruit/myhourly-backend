# Backend implementation of configurable Sandwich Leave policy

Implementation adds three independently configurable sandwich leave rules to the leave management system. The Monday rule forces preceding weekends to count as working days (3 days total). The Friday rule forces following weekends (3 days total). The Friday+Monday rule handles continuous Friday-through-Monday requests by forcing the intervening weekend (4 days total). The rules enforce precedence to prevent double-counting weekend days when multiple rules are enabled. The changes touch the database schema, entity layer, DTO layer, service logic, and test suite.

**Watch for:** frontend Settings UI missing from commit **(confirmed)**, potential LOP/PAID classifier gap if that service exists in main repo **(likely)**, empty file artifact `Mon-only)` in commit **(confirmed)**, Settings DTO fields marked `@NotNull` but no discussion of backward compatibility **(possible)**.

**Verdict**: NEEDS_CHANGES

## High-level view

The sandwich expansion algorithm correctly implements the three-rule precedence system: Friday+Monday first, then Friday-only if that didn't fire, then Monday-only if neither fired. This prevents weekend days from being added multiple times. The forced working days are stored separately in a JSON column on the leave request, allowing the original user-selected date range to remain unchanged while downstream systems can read the forced days list.

The DTO fields are marked `@NotNull` in the request DTO but the database columns have `DEFAULT false`, which means existing API clients that omit these fields will fail validation even though the database can handle the absence. This is a breaking change to the PUT endpoint contract unless clients are guaranteed to send all three fields.

The implementation touches the validation service and request service but the verification note flags that `LeavePaidLopServiceImpl` in the main repository likely needs modification to respect forced working days when classifying PAID vs LOP. The worktree doesn't contain that service, so this is an integration gap.

The frontend Settings.jsx file is specified in the design and plan but missing from the commit. This means the three sandwich settings cannot be toggled by users through the UI, making the feature incomplete for end-user configuration.

The test suite covers all three rules individually, rule precedence with all three enabled, edge cases including public holidays on forced weekends and month boundaries, and insufficient balance validation. The tests correctly verify that forced working days are populated and that the total day count reflects the sandwich expansion.

## Sandwich expansion algorithm and rule precedence

The algorithm iterates `requestDates` (the original user-selected dates) to detect trigger days (Friday, Monday) and breaks after finding the first match. This means if a user applies for two separate Fridays in a multi-week request, only the first Friday triggers the Friday rule. This is consistent with the requirement that each rule fires "once per request," but it's worth confirming this single-trigger behavior matches the business intent.



## Forced working days persisted as JSON in LeaveRequest entity

The serialization hooks log warnings on failure but continue, setting the JSON field to null if serialization fails. This means a serialization error would silently drop the forced working days. The risk is low since `LocalDate` is well-supported by Jackson.



## DTO fields marked @NotNull in LeaveSettingsRequest break backward compatibility

The three new fields in `LeaveSettingsRequest` are annotated `@NotNull`, which means the request validator will reject PUT requests that omit these fields. The database migration adds the columns with `DEFAULT false`, so the database can handle the absence, but the DTO layer cannot. This is a breaking change to the API contract. Existing clients that PUT settings without including the three new fields will receive a 400 validation error.

The backward-compatible approach would be to make the request fields nullable (`private Boolean sandwichLeaveMondayEnabled;` without `@NotNull`) and have the mapper default them to `false` if null.





## Test coverage comprehensive with edge cases

The `LeaveSandwichPolicyTest` class includes 15 test cases covering all three rules individually, rule precedence with all three enabled, public holidays on forced weekends, month boundaries, and insufficient balance validation.

The test case `testFridayRuleCrossingMonthBoundary()` uses Friday Oct 27, which is mid-month. Oct 27 + 2 days = Oct 29, which is still October. The test passes but doesn't validate the edge case its name suggests.

## Frontend Settings UI missing from commit

Without the frontend UI, administrators cannot enable or disable the sandwich leave rules through the settings page.



## LeavePaidLopServiceImpl integration gap

The verification note and design document both flag that the main repository's `LeavePaidLopServiceImpl` PAID/LOP classifier must be updated to read `forcedWorkingDays` from LeaveRequest and count them as working days even if they fall on weekends. Without this change, the PAID/LOP split will incorrectly skip the forced weekend days, meaning those days will not be charged against the monthly PAID guideline or the leave balance. This would break the sandwich leave feature's core functionality.

The worktree does not contain `LeavePaidLopServiceImpl`, so it cannot be fixed in this commit. This must be documented as a follow-up task or the implementation must be moved to the main repository where both services can be modified together.
